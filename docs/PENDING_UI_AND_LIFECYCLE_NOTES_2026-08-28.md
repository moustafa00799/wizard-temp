# ملاحظات واجهة وتجربة العميل مؤجلة — 2026-08-28

هذه الوثيقة تسجل الملاحظات الحالية فقط. **لا يُنفذ أي تعديل برمجي اعتمادًا عليها حتى يرسل المستخدم بقية الملاحظات ويؤكد بدء التنفيذ.**

## الملاحظة الأولى: Knowledge Context

قائمة اختيار `Knowledge Context` الظاهرة داخل Wizard ليست الشكل النهائي المقصود للعميل. المطلوب لاحقًا إزالة اختيار السياق المعرفي من العميل، وجعل الخادم يطابق تلقائيًا السياق المنقح والمسموح به وفق workspace والسوق والصناعة والفترة والنطاق. إذا لم يوجد تطابق، تستمر النتيجة دون سياق إضافي مع سبب `unavailable`. يظهر السياق المستخدم في Blueprint كـread-only provenance فقط.

يبقى اختيار تشغيل أو عدم تشغيل **AI الاستشاري** منفصلًا عن Knowledge Context، ولا يجوز للسياق أو AI تغيير Canonical Blueprint أو قرارات CDKS أو الميزانية أو الحملات.

## الملاحظة الثانية: Lifecycle Review

النص أو التدفق المرتبط بـ`إرسال إلى Review` يظهر ملاحظة:

> Human lifecycle transitions require `actor_user_id`.

يجب مراجعة سبب ظهور هذه الرسالة مع بقية ملاحظات المستخدم قبل التعديل. القرار المبدئي الآمن هو أن تُشتق هوية المراجع من session server-side، لا أن يُطلب من العميل إدخال معرف يدوي أو أن يُقبل معرف غير موثق من body. لا يُنفذ هذا القرار قبل اكتمال الملاحظات والتأكيد.

## قيود ثابتة أثناء الانتظار

لا تغيير في الكود الآن. لا تغيير في Canonical Blueprint أو CDKS authority. لا provider write ولا Publish ولا Spend. يظل AI استشاريًا فقط، وتظل `marketValidated=false` و`blueprint_only=true`.

## الملاحظة الثالثة: قيم Blueprint غير المحددة

تظهر حقول مثل `content` و`KPI` و`industry_average_cvr` و`industry_average_ctr` و`target_cpa` و`performance_targets` و`weekly_projection` و`daily_targets` و`cpc_expectation` و`competition_level` بقيم غير محددة أو `unavailable`. هذه ليست كلها أخطاء عرض؛ يجب تدقيق كل حقل مقابل عقد Blueprint ومصدره.

القاعدة المطلوبة هي التفريق بين:

- قيمة يمكن اشتقاقها بأمان من Wizard أو CDKS، ويجب عرضها للعميل بصياغة مفهومة.
- قيمة تحتاج evidence أو benchmark خارجيًا موثقًا، وتبقى `unavailable` مع سبب مبسط.
- قيمة اختيارية لا تنطبق على الحالة، ويجب عرضها كـ«غير منطبق» بدل «غير محدد».
- قيمة ناقصة بسبب خطأ في mapping أو renderer، ويجب إصلاحها برمجيًا.

لا يجوز ملء هذه الحقول بأرقام أو benchmarks مخترعة. ينبغي تحديد ما إذا كانت القيمة غير متاحة بسبب سياسة الأدلة أو بسبب نقص في الـWizard أو بسبب خلل في التحويل قبل تغيير العرض.

## الملاحظة الرابعة: تسريب كود renderer إلى الواجهة

ظهور نص مثل:

`function StatusPill({ status }) { ... }`

مع تفاصيل Turbopack و`jsxDEV` هو خلل عرض واضح، وليس حالة `unavailable` صحيحة. يجب عزل الدوال البرمجية عن بيانات العرض، والتحقق من سبب تمرير function source أو dev-render artifact إلى `displayValue`/StatusPill. لا يجوز أن يظهر أي source code أو stack/framework internals للعميل.

## الملاحظة الخامسة: التكرار في العناوين

تم توضيح أن تكرار عناوين `Claims` و`الأدلة` في النص المنسوخ سببه تكرار النسخ من المستخدم، وليس دليلًا مؤكدًا على خلل في الواجهة. لا يُنفذ تغيير لهذا السبب وحده، مع إبقاء تدقيق بنية التبويبات مطلوبًا عند إعادة التصميم.

## الملاحظة السادسة: ترابط الأقسام وخطة الدمج المبدئية

ينبغي مراجعة الأقسام الستة والعشرين وتصنيفها إلى طبقات عرض بدل عرضها كقائمة مسطحة. التصميم المبدئي المقترح للمراجعة:

| طبقة العرض | الأقسام المرتبطة | الهدف |
|---|---|---|
| ملخص القرار | الهدف، الجمهور، القنوات، نوع الـFunnel، الملخص التنفيذي | فهم ما قرره النظام بسرعة |
| الاستراتيجية والتنفيذ | الرسائل، المحتوى/الإبداع، خطة الاختبارات، التوقيت، خطة الإطلاق | تحويل القرار إلى خطوات عملية |
| الميزانية والقياس | إدارة الميزانية، المؤشرات المرجعية، Measurement Plan، أهداف الأداء | توضيح ما يمكن قياسه وما يزال unavailable |
| السوق والسياق | سياق السوق، الموسمية، المنافسة، العرض/التمايز | عرض السياق الاتجاهي دون ادعاء Market Validation |
| الجاهزية والمخاطر | التحذيرات، الامتثال، التدقيق التقني، readiness | معرفة ما يجب مراجعته قبل الاعتماد |
| التفاصيل والتتبع | provenance، الأدلة، AI Reasoning، سجل التغييرات، lifecycle | طبقة متقدمة للمراجع والمطور |

يجب عدم الدمج اعتمادًا على تشابه العنوان فقط؛ كل مجموعة تحتاج مطابقة مع عقد البيانات ومصدر الحقول واحتياجات المستخدم. الأقسام التي تحمل تحذيرات يمكن دمجها في مركز «الجاهزية والمخاطر» مع إبقاء نوع التحذير واضحًا، لا حذف التحذيرات.

## قيود التنفيذ

لا يتم تعديل UI أو contracts أو mapping الآن حتى تكتمل ملاحظات المستخدم. بعد اكتمالها تُجرى مراجعة source-to-renderer لكل حقل، ثم يُصمم wireframe/Information Architecture، ثم تُنفذ التغييرات مع regression للبيانات ولقطات العرض. تبقى سلطة CDKS وCanonical Blueprint ثابتة، وAI استشاريًا فقط، و`marketValidated=false`.

## نتائج التدقيق البرمجي الأولي

مسار `/api/generate/v5` يستخدم `CDKSEngine` ثم يمرر الناتج عبر `CanonicalBlueprintSchema` و`buildBlueprintContractV3` قبل العرض. لذلك يجب ألا تُملأ القيم الناقصة من renderer نفسه؛ مصدرها يجب أن يُراجع في المحرك أو العقد.

عقد Canonical Blueprint يعرّف مؤشرات benchmark كقيم nullable، ويعرّف حالة benchmark كـ`available` أو `unavailable`. كما أن محرك CDKS الحالي يضع بعض الحقول market-dependent صراحةً كـ`null` أو `unavailable` عند غياب مصدر موثوق، وهو سلوك يجب الحفاظ عليه مع تحسين صياغة العرض فقط.

تدقيق الميزانية أظهر أن عقد Canonical Blueprint يتطلب `monthly_pacing` و`daily_targets` و`weekly_projection`، بينما يجب مقارنة البيانات الفعلية التي يعيدها المسار مع هذه البنية؛ إذا كانت القيم موجودة في payload ولا تظهر، فالمشكلة في mapping/renderer وليست في سياسة الأدلة.

تدقيق Knowledge Context أظهر أن generate v5 يقرأ حاليًا `knowledge_context_id` من body، ويقبل مسار `knowledge_strategy_selection` في بيئة غير production. هذا مناسب للاختبارات السابقة، لكنه يتعارض مع المتطلب النهائي القائل إن العميل لا يختار السياق. عند تنفيذ الدفعة اللاحقة يجب نقل الاختيار إلى server-side deterministic matching، مع إبقاء provenance read-only للعميل.

تظل ملاحظة تسريب `function StatusPill` غير محسومة المصدر من النص المنسوخ وحده؛ يجب إثباتها باختبار DOM/render أو payload قبل تغيير helper، مع إضافة guard يمنع عرض function source أو framework internals في جميع الأحوال.

## نطاق تطوير مؤجل بعد الدفعة الحالية

طلب المستخدم تأجيل مناقشة وتنفيذ المحاور التالية إلى ما بعد إغلاق الإصلاحات المحصورة واختبارها:

1. إعادة تسمية وصياغة كامل محتوى Blueprint بمصطلحات سوقية وتسويقية وصناعية مفهومة للعميل.
2. دعم العربية والإنجليزية على مستوى Wizard وBlueprint والنتائج، مع اختيار لغة العميل، ودراسة ما إذا كان ذلك يتطلب i18n كاملًا أو طبقة عرض مترجمة فوق Canonical Blueprint.
3. إعادة تقييم Information Architecture والشكل العام للنتائج ليكون مترابطًا وقابلًا للبحث والقراءة بسهولة.
4. توسيع دور AI مستقبلًا من الاستشارة إلى دعم أوسع للـRules Engine، وتحليل المنافسين والسوق وSWOT، مع integrations ومصادر معتمدة، وإنشاء محتوى وhooks وscripts ومواد إعلانية متعددة، مع بقاء CDKS وCanonical Blueprint السلطة النهائية.
5. توسيع AI Reasoning ليقدم شرحًا مهنيًا أعمق لأسباب التوصيات والبدائل والمخاطر والقيود، بصيغة تشبه تفسير Media Buyer أو Marketer، مع بقاء كل الادعاءات مقيدة بالأدلة وعدم السماح للـAI بتغيير القرارات الحاكمة.

هذه المحاور **لا تُناقش أو تُنفذ الآن**. ستُدرس كخطة مستقلة بعد إغلاق: إصلاح renderer، تدقيق القيم غير المحددة، توحيد حالات العرض، تنظيم الأقسام، وضبط Lifecycle وKnowledge Context.
